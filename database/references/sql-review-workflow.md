# SQL 识别审查与精准编写工作流

本文件定义两条核心工作流的详细步骤与输出格式，是 SKILL.md 流程 A/B 的操作手册。

## 流程 A：图片 SQL 识别与差错审查

### A1. 读取图片
- 用户提供图片文件路径时，用 Read 工具读取图片（支持 PNG/JPG 等），从图中识别 SQL 文本
- 用户直接在对话中发送图片时，直接查看识别
- 识别障碍处理：图片模糊/倾斜/遮挡 → 识别出能确定的部分，无法确定处标注 `[?]`，并向用户确认

### A2. 原样打印
输出格式（必须完整，不改写）：

```sql
-- 识别结果（Oracle 方言）
SELECT ...
```

- **必须原样打印识别出的 SQL**，不提前修改
- 同时标注：识别目标数据库（Oracle/MySQL/PG）、SQL 大致用途（查询/更新/建表）

### A3. 五维差错扫描

按以下五个维度逐项检查，每个维度输出检查结果：

```
① 语法检查
   - Oracle 方言语法：分页(ROWNUM/FETCH)、NVL、TRUNC、|| 拼接
   - 括号配对、引号闭合、逗号遗漏、关键字拼写
② 表名/字段名检查（对照 collection20-tables.md）
   - 表是否存在、大小写（Oracle 表名大写）
   - 字段是否存在、是否拼错（如 PAP_R 误写为 PAP_R1）
   - schema 前缀是否正确（SG_MIS./SGAMI_STAT./IEOM.）
③ 业务逻辑检查
   - 电量字段方向/费率是否用对（PAP/PRP/RAP/RRP、E/R/D）
   - 统计口径（日/月表选错、DATA_DATE vs STAT_DATE）
   - 代码值是否符合标准代码（对照 collection20-codes.md）
   - 关联字段类型/逻辑是否正确（DATA_ENTITY_ID 关联）
④ 性能隐患
   - SELECT *（应列明字段）
   - 大表无过滤条件、函数包裹索引列、隐式类型转换
   - 深分页 OFFSET 过大
   - 无必要 DISTINCT/ORDER BY
⑤ 标准代码使用
   - 枚举值是否正确（如用户类型 01专变/02公变/03低压）
   - 异常类型码段是否正确（01xx采集/02xx计量/...）
```

### A4. 逐句解释

用业务语言逐条说明，例如：
- `FROM A_BA_CONS_ENERGY_DAY` → "查用户日电量统计表"
- `WHERE MGT_ORG_CODE='32'` → "限定江苏电力（省公司）"
- `SUM(PAP_E1)` → "汇总正向有功尖峰电量"

### A5. 询问优化

输出格式：

```
【扫描结论】
⚠️ 错误（必须修复）：
  - ...
💡 建议（可优化）：
  - ...
是否需要我对该 SQL 进行优化？【是/否】
```

- 有错误 → 说明原因，等待用户确认后修复
- 无错误但可优化 → 给出优化建议，询问是否应用
- 完全没问题 → 明确说明"未发现问题"，仍可询问是否需要优化写法

## 流程 B：SQL 精准编写

### B1. 确认目标表
- 用户给表名 → 在 `collection20-tables.md` 查找，确认：所属域、schema 前缀、关键字段
- 用户只给业务描述（如"查用户日电量"）→ 根据业务域推荐表（A_BA_CONS_ENERGY_DAY）
- 表不确定时向用户确认，不擅自假设

### B2. 确认业务意图
需确认的要素：
- 查询对象：用户/计量点/电能表/台区/单位/行业
- 时间范围：日/月/指定区间
- 统计口径：总量/分费率/分相/趋势
- 过滤条件：管理单位、用户类型、电压等级等
- 输出要求：明细 or 汇总、排序、分页

### B3. 编写 SQL
- 默认 Oracle 方言（采集2.0）
- 优先复用 `collection20-sql-patterns.md` 模板
- 遵守规范：字段列明（不用 *）、别名用英文或 AS 中文、时间过滤用日期函数、代码值用字典

### B4. 自检清单
- [ ] 表名/schema 前缀正确
- [ ] 字段名与表结构一致（对照表速查）
- [ ] 代码值符合标准代码字典
- [ ] 统计口径正确（日/月表、DATA_DATE/STAT_DATE）
- [ ] 性能合理（有索引列过滤、无 SELECT *）
- [ ] 方言正确（Oracle 分页/函数）

### B5. 交付格式

```sql
-- 说明：查询目的
SELECT ...;
```

交付后附：
- **选表依据**：为什么用这张表（业务含义）
- **口径说明**：统计范围、时间、过滤条件
- **可调整点**：如"如需分费率汇总，可把 PAP_E1~E6 分别 SUM"

## 交互总则

1. 识别与编写都遵循"**先完整呈现，再解释，再询问**"
2. 用户说"优化"时按扫描结论逐项修复，修复后给出对比（原 SQL vs 新 SQL）
3. 修复后复述修改点，让用户确认
4. 涉及 DELETE/UPDATE 必须先用 SELECT 预览影响行数
5. 不擅自在对话中执行 SQL（无数据库连接时仅提供语句）；如配置了数据库连接，执行前先征得同意
